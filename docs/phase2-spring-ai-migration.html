新增了什么能力

NEW

Spring AI ChatClient 驱动 Agent

RecommendationAgent 从手写 RestTemplate + 手动 tool loop（~180 行）改为 Spring AI ChatClient 声明式调用（~80 行）。工具调用、消息管理由框架自动处理。

NEW

@Tool 注解替代自定义 Tool 接口

5 个工具的 JSON Schema 从手写 Map<String,Object> 改为 Spring AI @Tool + @ToolParam 注解自动生成，参数从 JSON String 变为类型安全的 Java 参数。

NEW

ChatMemory 工作记忆

对话历史管理从手写 Redis String 读写改为 Spring AI ChatMemory + MessageChatMemoryAdvisor，历史注入完全自动，无需手动拼接 messages 列表。

NEW

SimpleVectorStore 向量检索

手写的 InMemoryVectorStore（余弦相似度暴力检索，~124 行）替换为 Spring AI 标准 SimpleVectorStore，embedding 计算内置，支持后续无缝切换生产级向量库。

NEW

TokenTextSplitter 分块

手写 CJK 感知分块器（~307 行）替换为 Spring AI TokenTextSplitter。基于 BPE tokenizer 的真正 token 计数，而非启发式字符估算。

NEW

ChatClient 结构化输出

PreferenceExtractor 从手写 RestTemplate + 脆弱的 JSON 子串提取改为 .call().entity(PreferenceProfile.class)，Spring AI 自动完成 JSON 解析和字段映射。

问题与设计动机

改动前

手写所有 Agent 基础设施

RecommendationAgent 用 RestTemplate 手动拼 HTTP body、手写 tool calling loop（含 tool_calls 解析、tool 执行、结果回填）、手写 tool JSON Schema。每加一个 tool 都要写三四十行样板代码。Embedding 和向量检索同样是 RestTemplate + 手写余弦相似度。

改动后

Spring AI 标准化模块替代

ChatClient 自动处理 tool calling loop；@Tool 注解自动生成 function schema；ChatMemory 自动管理对话历史；VectorStore 统一检索接口；TokenTextSplitter 做标准分块。业务 code 聚焦在 tool 的 execute 逻辑本身。

为什么选 Spring AI

框架选择考量

ai-code-helper 项目用 LangChain4j 自研了完整 Agent 框架——这证明了底层理解。CityLife Review 换用 Spring AI 证明"我知道业界标准怎么用"。两个项目投递时能讲出不同框架的优劣对比。Spring AI 的自动配置和 Boot 原生集成也减少了配置成本。

详细代码解读

agent/RecommendationAgent.java 重写 · ~180行 → ~80行

职责：Agent 核心编排器。负责构建 ChatClient、注册工具、注入记忆、调用 LLM。

关键改动：构造函数注入 ChatClient.Builder 和所有 @Tool bean，一次性配好 system prompt + memory advisor + tools：

@Component
public class RecommendationAgent {
    private final ChatClient chatClient;
    private final ChatMemory chatMemory;

    public RecommendationAgent(ChatClient.Builder builder, ChatMemory chatMemory,
            BlogTool blogTool, ShopSearchTool shopSearchTool, VoucherTool voucherTool,
            ReviewSearchTool reviewSearchTool, UserProfileTool userProfileTool) {
        this.chatMemory = chatMemory;
        this.chatClient = builder
            .defaultSystem(SYSTEM_PROMPT)
            .defaultAdvisors(new MessageChatMemoryAdvisor(chatMemory))
            .defaultTools(blogTool, shopSearchTool, voucherTool, reviewSearchTool, userProfileTool)
            .build();
    }

调用流程：

public RecommendResult recommend(String userMessage, String sessionId) {
    String conversationId = sessionId != null ? sessionId : UUID...;

    String reply = chatClient.prompt()
        .user(userMessage)
        .advisors(a -> a.param("chat_memory_conversation_id", conversationId))
        .call()
        .content();  // ChatClient 内部自动处理 tool calling 循环

    return new RecommendResult(reply, conversationId);
}

Review 要点：ChatClient 内部自动 loop（最多多少次？）取决于模型配置。SYSTEM_PROMPT 不变，规则 1-6 完全保留。

风险：ChatClient 默认 tool call 循环次数可能和原来手写的 8 轮上限不同，生产环境需要验证边界行为。

agent/tool/BlogTool.java（示例） 改造 · 5 个 Tool 统一模式

职责：从实现自定义 Tool 接口（手写 getName()/getDescription()/getParametersSchema()/execute(String)）改为 @Tool 注解 + 类型安全参数。

改动前 — 手写 JSON Schema：

public class BlogTool implements Tool {
    public Map<String, Object> getParametersSchema() {
        Map<String, Object> props = new HashMap<>();
        Map<String, Object> shopIdProp = new HashMap<>();
        shopIdProp.put("type", "integer");
        shopIdProp.put("description", "店铺ID");
        props.put("shopId", shopIdProp);
        // ... 每个参数都要写 ~5 行样板
    }
    public String execute(String argumentsJson) {
        JSONObject args = JSONUtil.parseObj(argumentsJson);  // 手动解析 JSON
        Long shopId = args.getLong("shopId");
        // ...
    }
}

改动后 — @Tool 注解：

@Component
public class BlogTool {  // 不再 implements Tool
    @Tool(description = "获取某个店铺的用户点评/日记列表...")
    public String getShopBlogs(
            @ToolParam(description = "店铺ID") Long shopId,
            @ToolParam(description = "返回条数，默认5，最大10") Integer limit) {
        // 参数直接是 Long 和 Integer，无需 JSON 手动解析
        if (shopId == null) return error("shopId不能为空");
        // ... 业务逻辑完全不变
    }
}

Review 要点：业务逻辑一行没改。删了 getName()/getDescription()/getParametersSchema() 三个方法共 ~25 行/tool × 5 tools = ~125 行样板代码。参数从 JSON String 变为类型安全的 Java 参数，NPE 风险从运行时前移到编译期。

rag/RAGService.java + ReviewIndexService.java 重写

职责：RAGService 负责语义检索 + 上下文构建；ReviewIndexService 负责启动时将 Blog 数据分块入库。

关键改动 — RAGService：原来手动调 EmbeddingService.embed() 再手动调 VectorStore.search()，现在 VectorStore 内置 embedding：

public List<RetrievalResult> search(String query, int topK, String sourceType) {
    // VectorStore 内部自动 embedding，无需手动调用 EmbeddingService
    List<Document> docs = vectorStore.similaritySearch(
        SearchRequest.builder().query(query).topK(topK * 2).build());

    // Java 侧过滤 sourceType（SimpleVectorStore 的 filter 支持有限）
    List<Document> filtered = docs.stream()
        .filter(d -> sourceType == null || sourceType.equals(d.getMetadata().get("sourceType")))
        .limit(topK).collect(Collectors.toList());
    // ... 装配 RetrievalResult，保留 citation 编号逻辑
}

关键改动 — ReviewIndexService：原来手动 new TextChunker(500, 50) 逐篇分块 → 手动 batch embedding → 手动 addAll，现在 TokenTextSplitter + VectorStore 一步完成：

@PostConstruct
public void init() {
    List<Blog> blogs = blogService.list();
    // 构造 Spring AI Document 列表
    List<Document> documents = new ArrayList<>();
    for (Blog blog : blogs) {
        Map<String, Object> metadata = new LinkedHashMap<>();
        metadata.put("sourceType", "blog");
        metadata.put("documentId", String.valueOf(blog.getId()));
        documents.add(new Document(blog.getTitle() + "\n\n" + blog.getContent(), metadata));
    }
    // TokenTextSplitter 分块 → VectorStore 自动 embedding 入库
    TokenTextSplitter splitter = new TokenTextSplitter();
    vectorStore.add(splitter.apply(documents));
}

Review 要点：分块质量是否有差异？手写 TextChunker 做了 Markdown heading 感知 + breadcrumb 路径记录 + CJK 特殊处理，TokenTextSplitter 是通用 BPE tokenizer。丢失了 heading path 元数据（生产可加自定义 DocumentTransformer 补回）。

agent/memory/PreferenceExtractor.java 重写 · ~140行 → ~80行

职责：用 LLM 从对话历史中提取结构化用户偏好画像。

关键改动：从手写 RestTemplate POST + 脆弱的 content.indexOf('{')...lastIndexOf('}') JSON 提取，改为 ChatClient.entity() 结构化输出：

public PreferenceExtractor(ChatClient.Builder builder) {
    this.chatClient = builder.defaultSystem(EXTRACT_PROMPT).build();
}

PreferenceProfile extract(Long userId, String dialogue) {
    // .entity() 自动处理 JSON 解析 + 字段映射，零手写 JSON 代码
    PreferenceProfile profile = chatClient.prompt()
        .user("请从以下对话中提取用户偏好：\n\n" + dialogue)
        .call()
        .entity(PreferenceProfile.class);
    if (profile != null) {
        profile.setLastUpdated(System.currentTimeMillis());
    }
    return profile;
}

Review 要点：提取 prompt 完全保留，对 LLM 输出质量无影响。结构化输出的可靠性提升：不再依赖 fragile 的 {} 括号定位。

删除的方法：getWorkingMemory()、saveWorkingMemory()、refreshWorkingMemoryTtl() — 这些现在由 ChatMemory 内部处理。

新增的方法：associateSessionUser(sessionId, userId)、getSessionUser(sessionId) — 用于在 Agent 请求之间关联会话和用户，方便 PreferenceExtractor 找到目标用户。

升级后 Agent 请求全流程

1. 用户发起请求 改动

POST /agent/recommend · AgentController.recommend()
接收 message + 可选的 sessionId。无 sessionId 时自动生成 12 位 hex。关联 session ↔ userId 到 Redis。
改动点 手动 MemoryService.getWorkingMemory() → ChatMemory 自动注入

2. ChatClient 构建系统上下文 新增

ChatClient.prompt().user(message).advisors(...) · RecommendationAgent
ChatClient 将 system prompt、MessageChatMemoryAdvisor 注入的历史消息、当前 user 消息合并为完整 prompt。不再手写 messages 列表构建。
分支 如果 sessionId 对应有历史对话 → MessageChatMemoryAdvisor 自动注入最近 N 轮对话

3. LLM 决策 + Tool 调用循环 简化

ChatClient.call() · Spring AI 内部处理
LLM 返回 tool_calls → Spring AI 自动匹配 @Tool 方法 → 类型转换参数 → 执行 → 结果回填。循环直到 LLM 返回纯文本。不再手写 8-round for 循环。
改动前 手写 JSONArray tool_calls 解析 + for 循环 + executeTool() → ~50 行代码全部由 ChatClient 内部完成

4. 返回结果 + 记忆留存 新增

chatMemory.get() → 组装 dialogue → PreferenceExtractor.extractAsync()
ChatMemory 自动保存本轮对话。Controller 从 ChatMemory 取出最近 20 条消息 → 拼成对话文本 → 异步调 PreferenceExtractor 提取偏好画像。
异步 extractAsync() 不阻塞主流程 → 失败仅 log error，不影响用户本次回答

5. 语义记忆持久化 保留

MemoryService.saveSemanticMemory(userId, profile) · Redis Hash
LLM 提取的 PreferenceProfile（菜系偏好、预算、氛围、confidence）写入 Redis Hash。UserProfileTool 下次查询时自动附加 semanticMemory 字段，Agent 即可个性化推荐。

掌握度自测与面试追问

基础理解

这次升级的核心动机是什么？
考察点：技术选型判断力
应答：Java 8 + Boot 2.3 是 2021 年的技术栈，Spring AI 不兼容。升级到 Boot 3.x + Java 17 后，可以用 Spring AI 标准模块替代 ~1000 行手写 Agent/RAG 基础设施代码，降低维护成本，同时和 ai-code-helper 的 LangChain4j 自研方案形成互补叙事——一个证明框架选型视野，一个证明底层理解。
为什么选 Spring AI 而不是 LangChain4j？
考察点：框架对比能力
应答：ai-code-helper 已经用 LangChain4j 自研了完整 Agent 框架（53 文件），再用 LangChain4j 等于两个项目技术同质化。Spring AI 是 Spring 生态的一等公民，自动配置完善，ChatClient API 声明式风格和 Boot 原生集成更自然。面试时能讲出两者优劣对比，比如 Spring AI 的 auto-config 更开箱即用，LangChain4j 的 Memory/Chain 抽象更灵活。

代码实现

手写 Tool 接口改为 @Tool 注解后，工具注册流程发生了什么变化？
考察点：Spring AI tool 机制理解
应答：以前是每个 Tool 手写 getName/getDescription/getParametersSchema 三个方法，RecommendationAgent 手动调 buildToolDefs() 构造 JSON Schema 数组，execute 时手动 JSON 解析参数。现在 @Tool 注解的方法由 Spring AI 自动扫描，生成 ToolCallback，参数从 JSON String 变为类型安全的 Java 参数（Long shopId, Integer limit），ChatClient 在 tool calling 时自动完成参数类型转换和验证。
MessageChatMemoryAdvisor 替代手动 working memory 管理后，对话历史的生命周期由谁控制？
考察点：ChatMemory 机制
应答：当前用 InMemoryChatMemory，生命周期 = JVM 进程，按 conversationId 隔离。生产环境可以替换为 Redis-backed ChatMemory 实现（需手写，Spring AI 1.0 暂无内置 RedisChatMemory），或利用现有的 MemoryService.associateSessionUser 作为桥接。

设计权衡

TokenTextSplitter 替代手写 TextChunker 丢失了什么能力？
考察点：分块器选型权衡
应答：手写 TextChunker 做了三件事 TokenTextSplitter 没做：① Markdown heading 层级感知 + breadcrumb 路径；② CJK 字符 1字符=1token 的启发式估算（中文场景比空格切词更准）；③ 段落级 overlap 抽取。TokenTextSplitter 用 BPE tokenizer 做真正的 token 计数，在中英混排场景更准确。生产建议用自定义 DocumentTransformer 补回 heading path 元数据。
如果 ChatClient 的 tool calling 陷入死循环怎么办？
考察点：边界风险意识
应答：原手写循环有硬上限 8 轮。ChatClient 默认无上限（或取决于模型 max_tokens）。可以通过 ChatClient.Builder 的 defaultOptions 设置或 prompt 中限制工具调用次数。生产建议加超时 + 监控告警。

面试高频追问

"手写 Agent 和用 Spring AI，你觉得哪个更好？"

回答要点 加分点 容易踩坑

回答要点：没有绝对的好坏。手写 Agent 让你理解 tool calling 的每一个环节——prompt 构建、function schema 生成、tool_calls 解析、结果回填。用框架则聚焦业务逻辑，迭代更快。我在 ai-code-helper 项目里从零实现了一个完整 Agent 框架，在 CityLife Review 里用了 Spring AI，两种模式都经历过，能在面试中讲清不同选型的适用场景。

加分点：能说出 Spring AI ChatClient 的 advisor 链模式（MessageChatMemoryAdvisor 只是其中一个 advisor，还可以加 QuestionAnswerAdvisor 做 RAG、自定义 advisor 做权限控制）。

容易踩坑：不要把"用框架"说成"懒得手写"——要强调"知道底层原理后主动选择框架提升效率"。

"这种大版本升级，你怎么保证不出问题？"

回答要点 加分点 容易踩坑

回答要点：分三步验证：① mvn clean compile 确保零编译错误；② 跑全量单元测试（11 个测试 0 失败）；③ 业务代码改动量最小——Controller、Service、Mapper 层一行没改，只做了 javax→jakarta 的 import 替换。最大的改动在 Agent/RAG 层，这些是新增能力而非修改现有逻辑。

加分点：能提到 docker-compose 同步升级（MySQL 5.7→8.0、ES 7.6→7.17）保证本地环境一致性。

容易踩坑：不要把测试结果当成"完全没问题"——需要强调集成测试和端到端验证还需要在真实环境跑。
