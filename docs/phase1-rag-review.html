问题与设计动机

改动前 按店铺查点评的局限

Agent 只能通过 getShopBlogs 按店铺 ID 精确拉取点评。用户问"哪家火锅店环境最好？"时，Agent 必须先搜出所有火锅店，再逐店调 Tool 拉点评。N 个店铺 = N+1 次 Tool 调用，常触发 8 轮限制。

改动后 跨店铺语义搜索

Agent 调一次 searchReviews，直接在全局点评中做语义检索。问题从"逐个店铺查"变成"一次查询全局命中"。检索结果带相似度排序和引用编号，LLM 可据此生成有信息来源的推荐。

设计理由 面试驱动：全手写 = 全链路可讲

不用 Spring AI / LangChain4j，因为面试时会被质疑"你只是调了个 API"。手写分块器、embedding 调用、余弦相似度检索、Tool 集成，每个环节都能展示对底层原理的理解。接口抽象让生产替换路径清晰。

详细流程：语义搜索全链路

1. 启动索引阶段
读取全量点评 新增
ReviewIndexService.init() — @PostConstruct
调用 IBlogService.list() 读取全部 Blog 记录。每条的 title + content 合并后送入分块器。
如果 Blog 表为空 → log warn，跳过索引。Agent 的 searchReviews 将返回空结果，自然回退到原有推荐路径。
文本分块 新增
TextChunker.chunk(text, "blog", blogId)
标题层级解析 → 段落切分 → CJK token 估算合并 → 生成带 headingPath 元数据的 chunk 列表。超长段落强制在句号处断开。
批量 Embedding 新增
OpenAIEmbeddingService.embed(texts) — POST /v1/embeddings
每批最多 20 个 chunk，发送到 OpenAI 兼容 API。返回 float[] 向量，维度由模型决定（如 text-embedding-3-small = 1536）。
如果 API 不可用（key 为空 / 网络不通） → catch 异常 + log error + 继续启动。RAG 功能静默降级，ReviewSearchTool 返回空结果。
写入向量存储 新增
InMemoryVectorStore.addAll(chunks)
Thread-safe 写入。至此全量点评的向量索引就绪，等待查询。后续可扩展为 MQ 事件驱动的增量索引。
2. 运行时查询阶段
用户发起请求
POST /agent/recommend → AgentController
用户输入自然语言："哪家火锅店环境最好？" → Controller 转发到 RecommendationAgent。
LLM 决策调用 Tool
RecommendationAgent.recommend() — tool-calling loop
LLM 分析用户意图，判断调用 searchReviews 比逐店拉取点评更高效。Tool 定义通过 buildToolDefs() 序列化后传入每次请求。
语义检索 新增
ReviewSearchTool → RAGService.search(query, topK, "blog")
查询文本 → embedding → VectorStore 余弦检索 → 返回带 citation 编号的结果 JSON。
LLM 合成回答
Agent 收到 tool 结果 → 注入 messages → next LLM turn
LLM 根据检索到的点评片段 + 引用编号，结合用户画像和其他 Tool 结果，生成带信息来源标注的自然语言推荐。

代码实现

TextChunker 的 CJK token 估算为什么重要？
考察点 分块策略的细节
中文字符间没有空格分隔，每个汉字 ≈ 1 token（英文需按空格切词）。如果用英文逻辑（按空格分词），整段中文会被当成一个巨型 "word"，分块功能失效。

加分回答：用 Unicode Block（CJK_UNIFIED_IDEOGRAPHS + Extensions A~E + 假名 + 韩文）而非简单的 char range 判断。同时承认 approxTokenLen 是估算值，生产可用 JTokkit 等精确 tokenizer 替换。
InMemoryVectorStore 为什么用 CosineOnWriteArrayList？
考察点 并发安全设计
ReviewIndexService（启动时 @PostConstruct 写）和 ReviewSearchTool（运行时请求读）存在并发场景。
COWAL 读操作无锁（只需底层数组的 volatile 读）、写操作全量复制。适合读多写少的场景（本项目写只在启动时一次，后续全是读）。

关键局限：认 COWAL 写时全量复制导致内存峰值 ×2。生产环境应换成 Redis Stack 或 Qdrant 等外部服务。
Embedding 的 batch size = 20 是怎么定的？
考察点 API 调用的工程考量
OpenAI embedding API 对 input 数组长度没有硬性限制，但 token 总量受模型上下文窗口约束。
20 个 chunk × 500 token ≈ 10,000 token，但 text-embedding-3-small 的单次限制是 8191 token —— 这里实际上对 token 量估算偏乐观。
因为是演示项目 + 数据量极小（~10 条），所以取了宽松值。生产环境应该改成 8-10 个 chunk/批，或增加 token 量预检。
ReviewSearchTool 返回的 JSON 在 Agent 循环中怎么被使用？
考察点 Agent tool-calling loop 理解
RecommendationAgent 的 tool-calling loop 中：
1. Tool 被执行 → 返回 JSON 字符串
2. 作为 role: "tool" 消息追加到 messages 列表
3. 下一轮 LLM 调用时，LLM 看到 tool 返回的 JSON + 之前的对话历史
4. LLM 决策是否还需要更多工具调用，或生成最终回答
5. 如果生成最终回答，LLM 会按 system prompt 要求用 [1][2] 标注引用来源

设计权衡

为什么 RAG 的 Generation 交给 Agent 而不是 RAGService？
考察点 职责划分
如果 RAGService 直接调 LLM 生成回答：
— Agent 会失去对回答风格的控制（system prompt 定义的语气、引用规范）
— 无法结合用户画像（getUserProfile）、优惠券（getShopVouchers）等 Tool 结果做综合推荐
— 架构上 RAG 模块就会从"检索服务"膨胀成"检索 + 生成服务"，职责不清
这套设计有哪些边界风险？
考察点 系统设计思维
1. 内存上限：10 万条 × 1536 维 × 4 字节 ≈ 600MB，不适合大数据量
2. 启动阻塞：@PostConstruct 中的索引在启动时同步执行，未来数据量大时启动变慢
3. 无增量更新：新点评发布后不会自动进入向量库，需重启或手动触发
4. 无质量评估：没有 hit rate / MRR / faithfulness 等检索质量指标监控
5. token 估算不精确：approxTokenLen 是估算值，batch size 偏乐观
如果让你继续优化，你会怎么做？
考察点 工程演进思路
Phase 2 — Agent 记忆：对话历史 + 用户偏好提取 + 语义记忆持久化，让推荐个性化
Phase 3 — 混合搜索：ES BM25 + 向量语义检索 → RRF 融合 + LLM 查询扩展（MQE）
增量索引：新 Blog 发布 → MQ 事件 → 实时更新向量库
质量评估：用 LLM 对检索结果做 faithfulness + relevance 评分，建立量化指标
向量库升级：Redis Stack (FT.SEARCH) 或 Qdrant，支持 HNSW 近似检索

面试高频追问

"你们项目的 RAG 是怎么做的？"

回答要点

从零手写全链路：TextChunker → OpenAIEmbeddingService → InMemoryVectorStore（余弦相似度） → RAGService 编排 → ReviewSearchTool 注入 Agent loop。每个组件留接口抽象，生产可替换。

加分点

Markdown 结构感知分块 + CJK Unicode Block 判断 + CosineOnWriteArrayList 线程安全设计 + COWAL 写时复制的内存代价分析 + 为什么不用 HNSW（数据量小，KNN 够用）。

容易踩坑

不要说"用了 LangChain / Spring AI" 或 "调了个 API"。面试官期待听到你对每个组件的底层原理和数学公式的理解。

"分块器为什么不用固定长度？"

回答要点

固定长度分块会切断语义单元 — 可能在句子中间断开，破坏上下文连贯性。Markdown 标题是天然语义边界，段落合并保持上下文。

加分点

CJK 字符 1 char = 1 token 的特殊处理。overlap 策略防止关键信息（如"这家店"的指代对象）跨越 chunk 边界丢失。超长段落在句号处断开而非硬切。

容易踩坑

不能说"固定窗口最常用所以选了它"。面试官期待听到你对语义边界的理解，以及不同分块策略（递归分块、语义分块、句子级分块）的对比。

"稀疏检索和稠密检索的区别？"

回答要点

BM25（稀疏）：基于词频-逆文档频率，对精确匹配、实体名、专有名词效果好。Embedding（稠密）：将文本映射到语义空间，擅长理解近义词和语义相似。

加分点

最佳实践是混合：BM25 召回 + 向量召回 → RRF (Reciprocal Rank Fusion，k=60) 融合 → reranker 精排。能说出 RRF 公式 Σ 1/(k+rank_i) 并解释 k=60 的含义。

容易踩坑

不要绝对化"稠密已经完全取代稀疏"。在实体搜索（人名、店名）上 BM25 仍往往更准。

"余弦相似度和欧氏距离怎么选？"

回答要点

余弦测方向、欧氏测距离。文本 embedding 的 magnitude 通常不重要（OpenAI embedding 已归一化），所以用余弦 ≈ 用内积，效果等价且计算更快。

加分点

能说出当向量已 L2 归一化时，余弦相似度和欧氏距离是单调等价的：||a-b||² = 2 - 2cos(a,b)。因此选余弦只因为直觉更自然，数学上没有优劣。

容易踩坑

不能说"随便选一个"。要说出关键词：方向 vs 大小、归一化、计算代价。

一分钟口述答案

我在 CityLife Review 这个 Spring Boot 项目中从零手写了一套 RAG 管线，让 Agent 能够对全站用户点评做语义搜索。 核心链路是：TextChunker 用 Markdown 标题层级做结构感知分块，CJK 字符按 1 token 估算； OpenAIEmbeddingService 复用项目已有的 API 配置调 embedding 接口； InMemoryVectorStore 基于 CosineOnWriteArrayList 做线程安全的余弦相似度检索； RAGService 编排 Retrieve + Augment，Generation 交给 Agent 的 LLM 以保留回答风格。 最后通过 ReviewSearchTool 实现项目已有的 Tool 接口，自动注入 Agent 的 tool-calling loop。 检索结果带 [1] [2] 引用编号。失败静默降级不影响主流程。17 个单元测试全部通过。
