新增了什么能力

🔍 智能查询改写

新增

解决的问题：用户问"那边贵不贵"，点评里写的是"人均80-120"，关键词完全对不上，直接搜啥都搜不到。

改动前：用户说啥就搜啥，口语查询直接扔进向量库。

改动后：AI 先把口语转成 2-3 个标准搜索词（"人均消费价格 性价比"+"消费水平 价位档次"），再去搜。

入口：QueryExpander.expandQuery()

📝 假想点评生成

新增

解决的问题：查询和点评文本之间的语言风格差异太大——问题很短很口语，点评很长很书面。

改动前：没有这个环节。

改动后：AI 先生成一段假想点评（80-150字），再把这段假点评转成向量去搜真点评。"用答案找答案"。

入口：QueryExpander.generateHyde()

🎯 语义结果精选

新增

解决的问题：向量搜索按数学距离排序，"距离近"不等于"对回答问题有用"。同一个词在差评和好评里用法完全不同。

改动前：向量搜回来按距离排个序就完事。

改动后：搜回一堆候选（约15-30条），让 AI 做语义判断——哪条真的在回答用户的问题，挑最好的。同时标注这是好评还是差评。

入口：ResultReRanker.rerank()

💾 向量持久化

改进

解决的问题：之前向量存内存里，每次重启服务索引全丢，重新索引几百条点评又慢又费钱（调用嵌入API）。

改动前：SimpleVectorStore，纯内存。

改动后：RedisVectorStore，存 Redis，重启还在。用独立的 Jedis 连接，不影响原有的缓存和分布式锁。

入口：RagConfig.vectorStore()

🏷️ 观点倾向标注

新增

解决的问题：Agent 推荐的时候不知道每条点评是在夸还是骂，只能按内容推荐，容易推荐到被差评的店。

改动前：只返回文本和分数。

改动后：LLM 重排序时顺带标注情感倾向（好评/差评/中性），Agent 看到差评会自动回避。

入口：ResultReRanker.RankedResult.sentiment()

改动前 → 改动后 → 为什么

改动前 最朴素的 RAG

用户说"朝阳区有没有适合约会的餐厅，别太贵"

→ 直接向量搜索"朝阳区有没有适合约会的餐厅，别太贵"

→ 问题：这句口语和点评文本的语言风格完全不同，向量搜到的往往不相关

→ 结果：召回质量靠运气

改动后 增强 RAG 管线

→ MQE 把问题改成"朝阳区 情侣约会 环境氛围" + "朝阳区 性价比 约会餐厅"

→ HyDE 生成假点评"上周去了朝阳区一家餐厅，灯光柔和很私密..."

→ 4 个查询各搜 N 条，合并去重

→ LLM 从候选里挑最相关的，标注好评/差评

→ 结果：每一步都在缩小语义差距

为什么 走语义路线而不是规则路线

我的另一个项目 ai-code-helper 走的是规则路线：60% 向量相似度 + 40% 关键词匹配。因为刷题场景里"动态规划""二叉树"这些词是精确的，关键词匹配很管用。

但点评场景不同："氛围好"和"环境舒服"说的是同一件事，但关键词完全不重叠。所以这边走语义路线——让 AI 理解用户到底想问什么，而不是靠关键词碰运气。

两条路线都做了，面试的时候可以对比论证。

🛡️ 防御性设计：管线里每一步都可能失败——MQE 挂了就少搜两路，HyDE 挂了就少搜一路，LLM 重排序挂了就退回按向量距离排序。每一步都有降级策略，最差情况下退化成原来的朴素搜索，不会比改之前更差。

代码精读

🔍 QueryExpander — 查询改写器

rag/QueryExpander.java · 新增

文件职责：接收用户的原始口语查询，输出 2-3 个改写变体 + 1 段假想点评。核心目的是填补"用户怎么说"和"点评怎么写"之间的语言风格差距。

MQE 改写 — 关键代码：

// 领域 Few-shot：告诉 AI 本地生活点评里常怎么说
private static final String MQE_PROMPT = """
    改写规则：
    "贵不贵" → "人均消费价格 性价比"
    "好不好吃" → "口味 菜品质量 推荐菜"
    "适合约会吗" → "环境氛围 私密 浪漫 适合两个人"
    ...""";

public List<String> expandQuery(String query, int numExpansions) {
    if (query == null || query.isBlank()) return List.of();
    // 调 LLM 做改写
    String response = chatClient.prompt().user(prompt).call().content();
        // 失败降级：返回空列表，不影响主流程
    catch (Exception e) { return List.of(); }
}

Review 重点：prompt 里给的几个映射例子是领域的 Few-shot——不给的话 AI 也能改写，但改写出来的词可能跟真实点评里的用词对不上。这段 prompt 是 recall 提升的主要来源。

HyDE 假想点评 — 关键代码：

public String generateHyde(String query) {
    // 让 AI 扮演"用户"，写一段假点评
    // 强调"不需要虚构店铺名称"——避免向量偏到具体实体
    String response = chatClient.prompt().user(prompt).call().content();
    // 失败降级：返回 null，RAGService 跳过多加一个查询
    catch (Exception e) { return null; }
}

为什么"不虚构店名"很重要？虚构了店名会让假点评的向量空间偏向那个名字，而不是偏向"这类体验"的语义。我们想要的是"约会体验"这个语义方向。

🎯 ResultReRanker — 结果精选器

rag/ResultReRanker.java · 新增

文件职责：接收一堆候选（15-30条），让 LLM 判每条跟原问题的相关度，挑出最好的 N 条，同时标注情感倾向（好评/差评/中性）。

关键代码：

public List<RankedResult> rerank(String query,
        List<RetrievalResult> candidates, int topK) {

    // 每条候选最多给 LLM 看 300 字，省 token
    if (text != null && text.length() > 300) {
        text = text.substring(0, 300) + "...";
    }

    // LLM 返回 JSON，扒掉可能的 markdown 代码块
    String json = extractJson(response);
    JSONArray arr = JSONUtil.parseArray(json);

        // 失败降级：按向量距离排序，情感写"中性"
    return fallbackRank(candidates, topK);
}

// 降级方法
private List<RankedResult> fallbackRank(...) {
    return candidates.stream()
        .sorted((a, b) -> Double.compare(b.score, a.score))
        .limit(topK)
        .map(r -> new RankedResult(r, r.score, "neutral", "向量分数"))
        .toList();

Review 重点：降级时 sentiment 写死 "neutral"，reason 写死 "向量分数"——将来 debug 时看到这两个值立刻能判断"这轮重排序失败了"。

风险点：重排序每次调 LLM，候选太多会消耗大量 token。截断到 300 字和限制候选池大小（通过 CANDIDATE_POOL_MULTIPLIER）是成本控制的关键。

掌握度自测

基础理解

这次改动新增了哪些核心能力？
基础 考察点：对改动范围的整体把握
关键词：MQE 多查询改写、HyDE 假想点评、LLM 语义重排序、观点标注、Redis 持久化

五个能力围绕一个目标：让用户说人话也能搜到想要的东西。每一步都在缩小"用户怎么问"和"点评怎么写"之间的语义差距。
改动前最核心的问题是什么？为什么直接用向量搜不够？
基础 考察点：对问题本质的理解
关键词：语义鸿沟、口语 vs 书面语、维度灾难

用户问"那边贵不贵"，点评写"人均消费大概在80-120之间"——关键词完全不重叠，向量空间里距离很远。

向量搜索本质上是在高维空间里找距离最近的邻居，但如果查询本身就偏离了你要找的东西的区域，最近邻居也不是你要的。

代码实现

为什么 MQE 和 HyDE 是两个独立的方法，而不是合在一起？
实现 考察点：设计粒度
关键词：独立降级、可选组合、成本控制

MQE 和 HyDE 失败的概率不一样——MQE 是结构化的"改写 N 个变体"，输出简单，失败率低。HyDE 要写一段合理的假点评，难度高，失败率也高。

分开之后可以独立降级：MQE 挂了不影响 HyDE，反之亦然。以后做 AB 测试也可以单独开关。
HyDE 的提示词里为什么强调"不需要完全虚构店铺名称"？
实现 考察点：prompt 工程细节
关键词：向量空间偏移、实体过拟合

如果 HyDE 虚构了"XX 咖啡厅"，生成的向量会把很多权重放在那个名字上，而不是放在"约会体验"这种抽象概念上。搜出来的结果会偏向包含那个名字的点评，而不是包含那种体验的点评。

设计权衡

为什么 LLM 重排序结果里要同时保留向量分数和 LLM 的相关度分数？
设计 考察点：信息冗余的价值
关键词：可观测性、debug、降级判定

两个分数合在一起能回答一个关键问题："LLM 认为这条很相关，但向量分数很低"——说明向量模型可能不适合查这类内容。

"LLM 认为这条不相关，但向量分数很高"——可能是关键词撞上了，但意思不对。

这些信息对后续优化方向（换嵌入模型？调整 prompt？）有直接指导意义。
这套设计和 ai-code-helper 的 RAG 走的相反路线，各自的代价是什么？
设计 考察点：跨项目对比分析
此项目的代价：LLM 依赖重——MQE + HyDE + 重排序三次调用 LLM，延迟高、成本高、稳定性差（每一步都可能出网络问题）。关键词搜索是免费的，LLM 调用不是。

ai-code-helper 的代价：规则不可泛化——HybridRanker 的 60/40 权重是在特定数据集上拍脑袋定的，换个场景要重新调。且关键词匹配遇到同义词完全无能为力。

什么时候用哪个：知识领域越规范（技术文档、代码、百科），规则路线越好。知识领域越自由（点评、评论、社交媒体），语义路线越好。

面试高频追问

Q1: "你做了这么多 RAG 增强，有没有做过量化评估？"

✅ 回答要点

保留了 searchBasic() 做 baseline。做了 20 条测试查询的 recall@5 对比。解释为什么 recall@5 比 recall@1 更适合这个场景（Agent 推荐需要多条候选）。

⭐ 加分点

不仅比"增强 vs 基础"，还比了"MQE 单独开 vs HyDE 单独开 vs 两个都开"的消融实验。能说出每一步贡献了多少。

⚠️ 容易踩坑

GPT 自己生成的评估数据有严重自评偏误——用同样的模型评估自己的输出。应该用人工标注或不同模型做评估。

Q2: "每次搜索调 3 次 LLM（MQE + HyDE + 重排序），延迟和成本扛得住吗？"

✅ 回答要点

延迟可控——每一步都有降级，而且 MQE 和 HyDE 可以并行调（两个独立调用）。重排序用了文本截断（300字）控制 token。实际上最慢的是嵌入调用，不是 LLM。

⭐ 加分点

提缓存策略：相同或相似查询的 MQE/HyDE 结果可以缓存。小红书/大众点评场景里热门查询重复率很高。

⚠️ 容易踩坑

说"延迟不重要"是错的。Agent 场景里每次工具调用都在用户等待中，3 次额外 LLM 调用可能增加 2-5 秒延迟。要承认这是权衡。

Q3: "SimpleVectorStore 换成 RedisVectorStore 之后，检索质量会变吗？"

✅ 回答要点

理论上不应该变——都是 COSINE 距离，同一个嵌入模型。但如果索引参数（HNSW 的 M 值、EF 值）没调好，近似搜索可能影响 recall。

⭐ 加分点

提 RedisSearch 的 HNSW 参数调优：M=16 适合中小规模（<1M 向量），EF_RUNTIME=10 是默认值但搜索精度可能不够。可以提"用 FLAT 暴力搜索做 ground truth 对比 HNSW 的 recall"。

⚠️ 容易踩坑

说"Redis 更快"——不一定。单机内存里搜比过网络快。换 Redis 是为了持久化，不是性能。

🗣️ 一分钟口述答案

我给 CityLife Review 的 AI 搜索做了三层增强。

第一层，让系统听懂人话：用户问"那边贵不贵"，系统不是直接搜这句话，而是先让 AI 把它改写成"人均消费价格 性价比"这种点评里常用的词，从多个角度去搜。

第二层，用答案找答案：让 AI 先生成一段假想点评，再用这段假想点评的语义去搜真点评，桥接过短口语和长篇点评之间的风格差距。

第三层，AI 精选：搜回来一堆候选之后，让 AI 做最终判断——哪条真的在回答用户的问题。顺带标注好评差评，帮推荐 Agent 避雷。

整个管线每一步都挂了都有备用方案，最差情况退回到原来的直接搜索，不会比改之前更差。同时把向量存储从内存换成了 Redis，重启不用重建索引。

我另一个项目 ai-code-helper 的 RAG 走的是规则路线，这边走的是语义路线——同一个问题在两种场景下走了相反的技术选型，我可以跟你聊聊各自的代价。
